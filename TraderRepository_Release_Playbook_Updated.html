04 / Verified Backtest Mechanic Basic example

1

Prepare source and version

Update the intended product’s private source. Verify its build workflow references the correct source filename, edition, app version, installer name and packaging configuration.

2

Run the private Windows workflow

Use Actions → relevant installer workflow → Run workflow. Wait for success. Do not publish from an incomplete or failed build.

3

Download the private draft installer

Open the private draft release generated by the workflow (use its direct link if needed) and download the exact .exe installer. Private draft release links are not suitable for public website buttons.

4

Smoke-test the Windows installer

Install and launch it. Check startup, expected edition and version, core UI and controls, and product-specific functionality. Confirm the installer filename matches the version being released.

5

Create a public release in the shared repository

Open TraderRepository-Downloads → Draft a new release. Create a unique tag for the product, edition and version, then enter a clear title and release notes. Example: backtestmechanic-basic-v1.0.0.

Do not use the generic v1.0.0 tag for multiple products in this shared repository. GitHub shows one repository-wide “Latest” release; every product site should use its own exact release asset URL.

6

Attach and publish the installer

Under Attach binaries, upload the tested .exe. Publish the release. Verify the asset is visible under Assets and the release is public, not a draft.

7

Verify the direct public installer URL

Copy the installer’s exact download URL from its release asset. Open it in a private/incognito browser without a GitHub login. If it returns 404, check the tag, asset spelling, publication status, and repository visibility.

8

Update the product’s root download.html

Set the HTML redirect and fallback link to the verified public installer URL. For Backtest Mechanic, the redirect file lives at the root of the product website repository, not download/index.html.

https://backtestmechanic.com/download.html

This is a redirect, not a download proxy. The branded website link hides the GitHub URL on the button, but GitHub can still appear in browser download details.

9

Connect every website download button

In the product website’s index.html, use href="download.html" for each installer button. Search the whole page for stale releases/download links and remove references to private -build releases. A “View GitHub Release” button is optional and can be removed from customer-facing pages.

10

Deploy and test the customer journey

Commit the website changes, wait for GitHub Pages to deploy, and hard-refresh. Hover over the orange download buttons: the browser status bar should show the product domain’s /download.html. Click and confirm the installer downloads without signing in. Test both hero and bottom download buttons.

03 / Publish a product release — complete procedure

Keep source private and build from the correct version

In the product’s private -build repository, verify the workflow references the intended Python entry point, app version, installer filename, and Inno Setup output path. Run its existing Windows workflow and confirm the resulting installer matches the intended edition.

Established pipeline: Python source → PyInstaller → Inno Setup → private draft GitHub Release → local Windows smoke test.

Avoid Actions artifact quota failures: existing working workflows publish the installer to a private draft release using gh release create rather than actions/upload-artifact. Preserve permissions: contents: write where required.

Do not assume all products use the same YAML filename. Check each repository’s actual .github/workflows/ files before changing any build configuration. Packaging Python into an EXE does not make reverse engineering impossible.

08 / Bitcoin checkout & local session recovery — preserve for paid products

Website checkout · Browser persistence · Cloudflare verification

Why we built this

Customers may close the payment popup, refresh the website, navigate away, or return later while a Bitcoin payment is pending. A temporary UI-only checkout would lose the quote, BTC amount, destination address, and transaction ID. The checkout therefore saves its recoverable session in the visitor's own browser using localStorage.

Important distinction: this is browser-local storage on the customer's computer, not a session file inside the installed Windows plotter. It survives ordinary refreshes and browser restarts in the same browser/profile, but it is not guaranteed across devices, private browsing, cleared site data, or disabled storage. The Cloudflare backend remains authoritative for payments and licenses.

What the Options Plotter website saves

  • Product identifier (the selected edition), so a resumed checkout uses the correct product.
  • Original quote: quote_id, quote_signature, required_sats, required_btc, bitcoin_address, and expires_at.
  • Transaction ID (TXID), checkout phase/status, and local save timestamp.
  • A Resume Payment control appears when a saved checkout is available. Reopening checkout restores the existing quote instead of silently starting over.

The current website code uses localStorage, not cookies, and stores a versioned JSON record. It handles blocked or unavailable browser storage without crashing the checkout.

Expected recovery behavior

A

Quote created

Save the returned quote immediately. Show the same BTC amount, address, and original expiration time when the checkout is reopened. Before a TXID is submitted, the countdown is based on the original quote expiry — never reset it by refreshing the page.

B

Popup closed or browser refreshed

Do not erase an unfinished checkout. Offer Resume Payment, restore the saved details, and allow the customer to continue.

C

TXID submitted

Validate the 64-character hexadecimal TXID, save it before verification, and stop treating the quote countdown as a reason to discard the pending payment. Keep the original quote and TXID available for retry and status checks.

D

Verification interrupted

Keep the checkout recoverable on network failure, timeout, popup close, or page refresh. A failed status request is not proof that payment failed. Let the customer retry verification or check saved status without sending another payment.

E

Confirmed or expired

Use the backend's verified status to decide whether a payment succeeded. Retain appropriate server-side records for recovery and replay protection. Clear or replace local state only when it is safe to do so; never lose an unresolved TXID.

Backend components to preserve

  • Cloudflare Worker: falling-sky-7997.traderrepository.workers.dev — checkout API and verification logic. The public site's code currently calls /premium/verify to verify a submitted TXID and /premium/status?quote_id=… to check saved payment state.
  • Cloudflare KV / D1: persistent payment and license records; keep quote/order identifiers, product mapping, verification outcomes, and replay protections consistent. Confirm the active bindings and schema before cloning to another product.
  • Bitcoin checks: blockchain verification (Blockstream in the existing design), correct receiving address, expected amount, confirmation threshold, and prevention of reusing a TXID for multiple purchases.
  • Timing rules in the established design: 60-minute quote validity, one blockchain confirmation, and the ability to complete verification after expiry when the TXID was registered in time. Verify the deployed Worker actually enforces these rules before launch.
  • Licensing: associate a confirmed payment with the correct product/edition and license or entitlement in D1; the browser's saved state alone never grants access.
Do not store secrets in localStorage. No private keys, signing secrets, API tokens, wallet seed phrases, or privileged license-generation credentials belong in website JavaScript or browser storage. Keep those on the Worker/server side.

Repeat this for each new product

  1. Copy the proven checkout UI, persistence, and recovery logic into the new product website.
  2. Give the product its own product IDs, names, versions, prices, and edition mapping; check both browser catalog and Worker-side catalog.
  3. Choose a distinct localStorage key per product/site, with a versioned record format. Avoid accidentally resuming another product's checkout.
  4. Point the site at the intended Worker API; configure approved site origins/CORS and any required routes or domain settings.
  5. Verify the Worker’s KV/D1 bindings, product-to-license mapping, and idempotent order/transaction handling before accepting real payments.
  6. Test refresh → resume, close popup → resume, browser restart → resume, TXID → network failure → retry, expiry before TXID, confirmation after timely TXID, and duplicate TXID rejection.
  7. Test both same browser recovery and server-side recovery. Local storage alone cannot restore checkout on a different computer or after site data is cleared.
  8. Do not overwrite a pending paid order with a new quote without checking its saved status first.

Current reference files: public OptionsPlotter/index.html (checkout and localStorage recovery) and the existing Cloudflare Worker implementation. Keep a separate private copy of Worker source, configuration, D1 migrations, and KV binding names for repeatable deployments.

08 / Exact click-by-click: private EXE → public raw link → branded download

Use this procedure for every product release. Example: Options Plotter Basic v1.0.0. The private build release is only where you retrieve the installer. The public shared release is where customers download it.

1

Download the finished EXE from the product build repository

Open OptionsPlotter-build → Releases. Open the completed Basic private build release, expand Assets, and click OptionsPlotter_Basic_Beta_v1.0.0.exe. Save the actual EXE to your computer (e.g. Downloads). Do not copy the private release URL as your public download link. Optionally install and smoke-test this exact EXE before publishing.

2

Open the shared public downloads repository

Visit TraderRepository-Downloads → Releases. Click Draft a new release (or Create a new release). This is the public repository, not the product's -build repository.

3

Create the tag, title and description

Click Choose a tag → Create new tag, enter optionsplotter-basic-v1.0.0, and choose target main. Set release title to Options Plotter Basic Beta v1.0.0. Add a short description stating that this is the Windows Basic Beta installer. Keep the product name, edition, version and installer filename consistent.

4

Upload under “Attach binaries”

Scroll to Attach binaries by dropping them here or selecting them. Drag the EXE downloaded in step 1 into that box, or click the box and select the file. Wait until OptionsPlotter_Basic_Beta_v1.0.0.exe appears as an uploaded asset. This is the binary attachment; do not upload the Python source ZIP, repository ZIP, or a text link.

5

Publish the release

Click Publish release (not Save draft). Open the published release page and verify the EXE appears under Assets. Example public release: Options Plotter Basic v1.0.0.

6

Get the FULL raw installer URL

On the public release page, under Assets, right-click the .exe filename and choose Copy link address. That is the full direct binary link. It must contain TraderRepository-Downloads/releases/download/, followed by the exact release tag and EXE filename. Paste it into a new private/incognito browser window to verify it starts a download without signing into GitHub.

Verified Options Plotter Basic direct link:

https://github.com/MarkB2026/TraderRepository-Downloads/releases/download/optionsplotter-basic-v1.0.0/OptionsPlotter_Basic_Beta_v1.0.0.exe

Wrong link: github.com/MarkB2026/OptionsPlotter-build/releases/download/... — that points to the private build repository.

7

Create download.html in the product website repository

Open the OptionsPlotter website repository. Select Add file → Create new file, type download.html as the filename (at repository root, beside index.html), paste the HTML below, then click Commit changes. If the file already exists, open it, click the pencil icon and replace only the redirect URL with the new verified public URL.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="robots" content="noindex,nofollow">
  <title>Downloading Options Plotter...</title>
  <meta http-equiv="refresh" content="0;url=https://github.com/MarkB2026/TraderRepository-Downloads/releases/download/optionsplotter-basic-v1.0.0/OptionsPlotter_Basic_Beta_v1.0.0.exe">
</head>
<body>
  <p>Starting your download...</p>
  <a id="file" href="https://github.com/MarkB2026/TraderRepository-Downloads/releases/download/optionsplotter-basic-v1.0.0/OptionsPlotter_Basic_Beta_v1.0.0.exe">Click here if the download does not start</a>
  <script>location.replace(document.getElementById('file').href);</script>
</body>
</html>

When changing versions, update both copies of the public EXE URL in this file: the meta refresh and the fallback anchor.

8

Update all Basic Download buttons in index.html

In the product website repository, open index.html → Edit. Find each Basic installer download button (top hero, lower page, popups if applicable). Change only its link target to href="download.html". Preserve the existing button text and styling. Do not edit Premium checkout, Bitcoin payment scripts, Cloudflare Worker URLs, payment recovery, DNS or GitHub Actions. Commit changes.

&lt;a href="download.html"&gt;Download Basic Beta&lt;/a&gt;

Paid Premium: Do not change Premium purchase buttons to an unrestricted public EXE. Use a separate controlled delivery process or a dedicated Premium redirect only when intentionally approved.

9

Test the customer-facing branded link

Wait for GitHub Pages deployment. Open https://optionsplotter.com in a private/incognito window. Hover each Basic Download button: the destination should show https://optionsplotter.com/download.html, not GitHub. Click it and verify the installer actually downloads. Check the filename and ensure Premium checkout still works as before.

Branded customer URL: https://optionsplotter.com/download.html. This masks the link displayed on the website; it does not conceal GitHub as the actual file host from browser/network download details.

10

For the next version, repeat with the new tag and EXE

Build and download the updated installer; create a new public release/tag and attach its EXE; copy its exact new public asset URL; edit the two URLs in the existing download.html. Leave all Basic website buttons pointing to the same download.html. No Worker, DNS or YAML changes required.
